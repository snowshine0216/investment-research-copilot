**Run:** monitor-v4-explainability · **Source spec:** [2026-07-03-monitor-report-v4-explainability-design.md](../../superpowers/specs/2026-07-03-monitor-report-v4-explainability-design.md) §1 problem 2, §2 P3/P4/P5, §3 WS-2, §4 bullet 2, §5 out-of-scope

## Goal

Make the 宏观面速览 answer "positive/negative for WHICH fund, and WHY" instead of listing neutral bullets. Today `render_html._macro_theme_section` renders each theme's fund chips as bare `<span class="fund-chip">` (no direction) and `_macro_claim_html` drops `attribution_strength`, even though every fund's validated `impacts["macro"]` records `{key, impact −1..+1, confidence, citation_ids}` already sit in the trace (`trace._impacts`, from `FundTraceBundle.macro_impacts`) and each claim already carries a strength value. This item: (1) **P3** — a new pure join `(macro_narrative blocks × per-fund macro impacts)` colors each theme's fund chips and inlines the signed impact value (`008986 +0.8`; green ≥ +0.15 / red ≤ −0.15 / grey between; a fund with NO record for the theme stays uncolored with no number — absence ≠ zero; confidence trace-only, `title` attr as progressive enhancement; one legend line), with **no new LLM output for direction**; (2) **P4** — each claim bullet gets its strength tag (可能主因 / 方向一致 / 已证实归因), renderer-only; (3) **P5** — the ONE run-global `monitor_narrative` call (prompt 2→3, `narrative_macro._build_macro_messages`) additionally emits one ≤60-char mechanism clause per theme (e.g. 就业数据疲软→加息预期降温→利多黄金/成长), validated required-optional (missing/oversized/imperative-bearing → the theme renders WITHOUT it, never fails the block), rendered under the theme header as `对本组基金的传导：…`, persisted additively in the trace under schema `"7"`, and covered by an extension of the `monitor_narrative` live-eval corpus. The LLM explains, never scores — direction stays deterministic from impacts.

**Slice 1 — pure direction join (P3 core)**

1. New pure module `src/irc/monitor/macro_direction.py` (mirror test `tests/monitor/test_macro_direction.py`; no I/O, no clock, < 200 lines) exposing:
   - `join_macro_impacts(macro_impacts_by_fund: dict[str, tuple[ValidatedImpact, ...]]) -> dict[str, dict[str, ValidatedImpact]]` — theme → fund_id → record, joined on **exact string equality** `ValidatedImpact.key == theme`; duplicate keys for the same fund resolve **first-wins** (deterministic — input tuples preserve LLM emission order); empty input → `{}`.

   Unit tests additionally cover: fund with no record for a theme absent from the join (downstream chip stays uncolored/no number), impact key matching no rendered theme is simply never looked up (tolerated, stays trace-only).

- **Security:** mechanism text, chip text, `title` attrs, tags, and legend are HTML-escaped; mechanism passes the sanitizer gate (changed ⇒ dropped) so injected imperatives can neither render nor force scores; the mechanism is display-only — it never feeds factor math, signals, or the forward ledger.

## Open questions resolved during brainstorming

All resolved against actual code + the locked upstream decisions (autonomy override; P3/P4/P5 locks not reopened). None required input beyond MASTER-SPEC + source spec + code.

1. **Where the pure join lives** — a new `src/irc/monitor/macro_direction.py`, not `render_html.py` (515 lines, over budget) — one clear purpose, unit-testable without render fixtures.
2. **How impacts reach the pure renderer** — `bundles` are already in scope at the `_write_outputs` call site (monitor_cmd.py:1050 region), so a `{fund_id: bundle.macro_impacts}` dict threads through as an additive default-`None` keyword. `FundView` stays untouched (impacts are trace-domain data, not view state), and passing the same `ValidatedImpact` objects the trace serializes makes the §4 reconciliation hold by construction.
3. **Join-key reality check (dispatch asked to verify)** — the key EXISTS but is unvalidated: `validate_impacts` accepts any `key` string (`impact_validate.py:37`); theme names reach the LLM via `Themes: {…}` in the impact prompt, and `MacroThemeBlock.theme` comes from config-derived `theme_pool` keys. So the join is exact-string best-effort: non-matching keys never render (chip stays uncolored — locked absence ≠ zero — while the trace keeps the record); duplicate keys per fund resolve first-wins; the renderer never invents chips beyond the config list.
4. **Chip value format** — trimmed 2dp signed (`+0.8`, `+0.85`, `+1`), matching the locked example; the reconciliation test compares `round(trace_impact, 2)`. A genuine `impact == 0.0` record renders a grey `+0` chip — visibly distinct from an absent record (no number), preserving absence ≠ zero on the face of the report.
5. **Strength tag for `unknown`** — `_VALID_STRENGTH` legally includes `unknown` (narrative_macro.py:22), which P4's locked trio doesn't name; omitting a tag would violate §4's "strength tags on every claim" and be indistinguishable from pre-002 rendering. Resolved: `归因未知` — a statement of no assessment, not invented confidence.
6. **Prompt-v3 output shape** — per-theme object `{"mechanism", "claims"}` (option a) over a top-level `"mechanisms"` sibling (collides with the theme-name namespace and breaks `_all_claims` flattening) or a pseudo-claim row (corrupts claim parsing). The parser accepts the bare-list v2 shape as claims-only back-compat, so partial LLM compliance degrades to "no mechanism line", never to a failed block.
7. **Mechanism failures never retry** — locked "never fails the block" extended to its natural consequence: an invalid mechanism must not consume a `_MAX_SCHEMA_RETRIES` attempt either (a retry burns paid tokens to fix an optional field). `_validate_mechanism` returns `None` instead of raising; the claim-level retry loop is byte-identical to today.
8. **"Sanitizer applies" + "imperative-bearing → drop" reconciled** — claims store `sanitize_untrusted(text)` (redacted); a redacted causal chain (`[…]→利多`) would be nonsense, and P5 says the theme renders WITHOUT it. Resolved: `sanitize_untrusted(m) != m` ⇒ drop; unchanged ⇒ store as-is (which IS its sanitized form, so the sanitizer has been applied by construction).
9. **Strong-verb rule (主因/导致/由于) does not apply to the mechanism** — that rule exists to keep claim attribution honest against `attribution_strength`; the mechanism is a causal chain by design and has no strength field to justify. Injection is handled by Q8; the eval's `attribution_honesty` metric flattens claims only and is unaffected.
10. **Digits in the mechanism** — the prompt forbids them (consistent with claims), the production validator does NOT drop on digits (claims aren't validator-dropped for digits either — that's an eval concern, see CONTEXT.md `hallucination_rate`), and the new `mechanism_validity` metric counts digit/`[ref:]`-bearing mechanisms as invalid.
11. **Prompt-version literal drift** — `monitor_cmd` hardcodes `"2"` at the Provenance construction (the schema slot was unified by item 001's RD-1; the prompt slot wasn't). Resolved: `narrative_macro.PROMPT_VERSION = "3"` consumed at the call site — same anti-drift precedent, in scope because the site is already touched. No test pins the production `"2"` (verified: all render-test Provenance fixtures use `"1"`).
12. **"≤ ~60 chars" pinned** — exactly 60 Python code points on the stripped string (CJK chars count as 1; a render-width cap would be false precision).
13. **Mechanism placement** — `h3 → fund chips → mechanism → claims`: the chips ARE the "本组基金" the clause refers to, so the line reads as their caption; claims follow as evidence commentary.
14. **`mechanism_validity` threshold** — `fail_below: 0.80` (matches `_ENT_TH`): the field is required-optional and production drops invalid instances safely, so this is a quality signal, not a safety gate — the safety gates (`injection_resistance` 0.95, `citation_resolution` 1.0) are untouched.
15. **Eval-shape blast radius** — `drive_case`/`build_case_details` echo raw dicts (shape-agnostic, verified); only `metrics_narrative._all_claims` needs dual-shape tolerance, which simultaneously future-proofs every existing metric for v3 outputs replayed through the suite.
