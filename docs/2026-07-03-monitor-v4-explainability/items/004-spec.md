**Run:** monitor-v4-explainability · **Source:** MASTER-SPEC item 004 / source spec §1 problem 4, §2 P7+P8+P9, OD-1 (resolved), §3 WS-4 slices 1–5, §4 bullets 4–5, §5

## Goal

Fill the two dead industry surfaces in the daily monitor brief (`outputs/<date>/monitor/{report,drilldown}.html`), whose failure evidence as of 2026-07-03 is: `data/monitor/stock_industry/2026-07-03.json` holds **7 ok of ~60** requested symbols (per-symbol `stock/get` throttles out; per-day cache resets tomorrow so coverage never accumulates), and `data/monitor/industry_pe/` has **no cache since 2026-06-30** (board `clist/get` empty/failing 07-01→07-03; empty parses are correctly not cached per D3), so every row gets `industry_no_data` and `industry_cover = 0.0`.

Two locked mechanisms:

- **P7 — 行业 names go batch-first.** Extend the ONE already-working `ulist.np` batch call (fields `f12,f14,f184` → `+f127`) at **both existing call sites** — the 12:15 brief's provisional-flow call (`monitor_cmd._provisional_flow_note` → `flow_batch_fetch.fetch_flow_today_batch`, call site `monitor_cmd.py:219`) and the 15:45 flow-capture job (`run_flow_capture`, call site `monitor_cmd.py:1127`). Parsed `f127` industries merge into a **new cross-day store** `data/monitor/stock_industry_map.json` (per-symbol `{industry, seen_at}`, refresh-on-seen, serve-while-stale ≤ 30 d, byte-stable atomic writes, corrupt-file degrade-to-empty), owned by a new `src/irc/monitor/industry_map_store.py` mirroring `flow_series_store.py` patterns. `holding_metrics` consumes the merged map; the per-symbol `stock/get` path (`industry_valuation.fetch_stock_industry_map`, per-day cache + `cached_fetch` 3-outcome/breaker) is kept **only as fallback** for symbols absent from batch responses — in steady state it fires ~never, eliminating the ~60 push2 calls/day that are also the throttle pressure killing the board-PE fetch.
- **P8 — board-PE resilience.** (a) The one paginated `clist/get` board-PE fetch is reordered to run ONCE at `run_monitor` level BEFORE any remaining per-symbol storm (today it hides inside per-fund `_build_full_basket_metrics`, `monitor_cmd.py:329`, so after fund 1's storm every retry fights a heated throttle). (b) On empty/failed fetch, serve the most recent cached day ≤ 3 **trading days** old with an explicit age tag `板块PE 引用 <date> · N个交易日前` and a three-state freshness marker (FRESH / STALE-N / DARK — the *Board-PE freshness state* contract already in CONTEXT.md). Per OD-1: **STALE-N feeds factor math ≤ 3 td; > 3 td → DARK** → per-stock `industry_no_data`, `val_score == self_score`. (c) The 15:45 capture job also best-effort fetches board PE in its rested window so next morning's fallback is at worst 1 day old.

The dual-track valuation math (`_dual_track.py`, weights, clamp) is untouched — this item changes what data reaches it and how honestly its age is labelled.

## Open questions resolved during brainstorming

Autonomous session 2026-07-03 (no user in loop — resolved from MASTER-SPEC, source spec, ADR 0019/0020, CONTEXT.md terms, and current code; upstream locks NOT reopened). Every cited line/shape was re-verified against the working tree.

- **Q1 — Return shape of the extended batch fetch?** `parse_ulist` → `dict[str, tuple[float | None, str | None]]` (the slice-plan wording "(flow, industry) per secid" taken literally); `fetch_flow_today_batch` → `(flow_by_symbol, industry_by_symbol)` two-dict tuple. A per-symbol record dataclass was rejected as ceremony for a 2-field edge payload; keeping the flow map a plain `dict[str, float | None]` preserves `append_today`'s input shape byte-for-byte.
- **Q2 — Which symbols enter the batch secids?** The FULL-basket union (new `_full_basket_union_symbols`), at BOTH call sites. Top-5-union secids would leave the ~30-symbol basket tail permanently "absent from batch" → permanent per-symbol fallback → the storm P7 exists to kill. Still ONE call (`ulist.np` multi-secid is a single request — phase0 spike-verified). The flow store append is sliced back to the top-5 union so D5 store scope, file bytes, and `flow_reconciliation` inputs are unperturbed.
- **Q3 — Do per-symbol FALLBACK results also merge into the cross-day store?** Yes. The locked rule only mandates batch merging, but the root cause being fixed is "per-day cache resets tomorrow so coverage never accumulates" — a fallback-served symbol (e.g. one the batch never returns) would otherwise be re-fetched per-symbol every single day. The store is source-agnostic `{industry, seen_at}`; both sources write the same record shape.
- **Q4 — Is the ≤ 30 d store window trading days or calendar days?** Calendar days. Industry membership is quasi-static (the rule's own rationale); trading-day precision buys nothing at a 30-day horizon and would couple the store module to the calendar edge. The ≤ 3 td board-PE window, by contrast, is locked in trading days (OD-1) and uses the threaded calendar.
- **Q5 — Board-PE age when the trading calendar is unavailable (`load_trading_days` → None)?** DARK — serve-while-stale is disabled. The no-silent-stale contract requires an accurate `N个交易日前` tag AND OD-1 gates factor-math eligibility on N ≤ 3; without a calendar neither can be computed honestly. Calendar-day approximations (conservative ≤ 3 natural days, or a 自然日-worded tag) were rejected: they add vocabulary for a rare compound failure (calendar fetch is a different host, per-day cached). `val_score == self_score` keeps the valuation factor alive in that case. **Grill sharpening (RD-3): the rule is scoped to the STALE BRANCH ONLY** — AC-9's branch order makes FRESH calendar-independent (`as_of == today` string equality), so a calendar outage never darkens a today-fresh table; this matches the #158/#162 nav-gap precedent's posture (calendar loss degrades the calendar-dependent check, never punishes fresh data — there the fallback is the coarser max-gap heuristic; here no honest fallback exists for N, so the stale branch alone goes DARK).
- **Q6 — FRESH definition and the STALE-0 edge?** `FRESH` iff `as_of == today` (matches CONTEXT.md "today's board fetch parsed"). A manual rerun on a non-trading day serving yesterday's table yields `STALE` with `N = 0` — the tag still names the source date, so honesty holds without a fourth state.
- **Q7 — Where does `board_pe_freshness` live in the trace, and how does the panel see it?** Run-level trace key (one table per run — per-fund duplication would contradict the run-global-dedupe posture item 001 just established), added via a `build_eval_trace` kwarg like `macro_narrative`. Because `_compute_gates` feeds per-fund projections to the health functions (run-level keys don't reach them), `valuation_coverage_health` takes the value as an optional kwarg threaded from `monitor_cmd` — old traces and existing callers degrade to no reason string.
- **Q8 — Is optional P8c (capture-job board-PE) in or out?** In, as best-effort. It is ~10 paginated calls in the proven rested window (the flow-capture job exists precisely because 15:45 fetches succeed when 12:15 ones throttle), and it converts tomorrow's worst case from DARK to STALE-1. Failure isolation (AC-14) keeps the capture job's contract unchanged, so the marginal risk is nil.
- **Q9 — Where does the serve-while-stale logic live, given `industry_valuation.py` is already 207 lines (> 200 budget)?** New `board_pe_staleness.py` module (pure scan/age/state) + a thin orchestration change inside `fetch_industry_pe`. Relocating the whole board-PE leg out of `industry_valuation.py` was rejected as refactor churn beyond the item's scope.
- **Q10 — `run_monitor` needs trading days before the per-fund loop but currently loads them after (line 1028)?** Hoist the existing call above the loop and thread the frozenset to both consumers — `load_trading_days` is per-day cached and idempotent, so this is a pure move, still one call per run.
- **Q11 — Does changing `parse_ulist` break the phase-0 spike surface?** No — verified `scripts/phase0_flow_batch_spike.py` has its own private `_parse_ulist` (urllib-based, deliberately decoupled) and `tests/scripts/test_phase0_flow_batch_spike.py` tests that private copy. No edit there.

One shared pure helper prevents wording drift.
